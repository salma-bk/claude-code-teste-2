## What this is

A team task-planning app (Next.js App Router). Users log in, declare recurring weekly availability, and create tasks; the app auto-suggests an assignee + time slot for a task, which a human then validates or rejects onto a shared team calendar. UI copy and error messages are in French.

## Commands

```bash
npm run dev      # start dev server (Turbopack) at http://localhost:3000
npm run build    # production build
npm run start    # run production build
npm run lint     # eslint
```

Database (Prisma + Postgres, run from repo root):

```bash
docker-compose up -d           # start local Postgres (exposed on host port 5433)
npx prisma migrate dev         # apply/create migrations against DATABASE_URL
npx prisma generate            # regenerate the Prisma client after schema changes
npx prisma studio               # inspect data visually
```

There is no test suite configured in this repo.

Env vars live in `.env` (see `.env.example`): `DATABASE_URL` (points at the docker-compose Postgres) and `AUTH_SECRET` (NextAuth secret).

## Important: this is Next.js 16, not the Next.js in your training data

APIs and file conventions differ from older Next.js. Two things that matter most in this repo:

- **`src/proxy.ts` is the middleware file.** Next 16 renamed the `middleware.ts` convention to `proxy.ts` (same role: runs before routes render, used here to gate every non-public route behind auth and bounce logged-in users away from `/login`/`/register`). Do not reintroduce a `middleware.ts` — edit `src/proxy.ts`.
- Before writing code that touches routing, caching, or config conventions, check `node_modules/next/dist/docs/` for the current behavior rather than relying on prior Next.js knowledge.

## Architecture

**Auth**: NextAuth v5 (`src/lib/auth.ts`) with a Credentials provider — email/password checked against `User.passwordHash` (bcrypt) in Postgres, JWT session strategy. `session.user.id` is injected via the `jwt`/`session` callbacks and typed in `src/types/next-auth.d.ts`. All users are peers — there is no role/permission field on `User`; anyone can create tasks, assign them to anyone, and manage their own availability.

**Data model** (`prisma/schema.prisma`):
- `User` — has recurring `Availability` windows, one-off `TimeOff` exceptions, and both authored (`createdTasks`) and assigned (`assignedTasks`) `Task`s.
- `Availability` — recurring weekly free-time window (`dayOfWeek` 0-6, `startMinute`/`endMinute` as minutes since midnight).
- `TimeOff` — a specific date that overrides availability to fully unavailable.
- `Task` — has `durationMinutes`, `priority`, optional `deadline`, and a `status` state machine: `PENDING → SUGGESTED → SCHEDULED`, or `DONE`/`CANCELLED`. `assigneeId`/`scheduledStart`/`scheduledEnd` are null until a slot is suggested.

**Scheduling engine** (`src/lib/scheduling.ts`) is the core logic, used by the API layer, not the UI:
- `getFreeSlotsForUser` computes free intervals for a user in a date range: start from recurring `Availability` windows per day of week, drop any day with a `TimeOff` entry, then subtract busy intervals from tasks already `SCHEDULED`/`SUGGESTED` for that user (`subtractBusy` does interval subtraction).
- `findEarliestSlot` scans a list of candidate user IDs and returns the earliest free slot (across all of them) that fits a task's duration before its deadline (default horizon: 60 days out if no deadline).
- `getAvailabilitySummary` aggregates free slots into day-count + total-minutes, used by the dashboard.

**Task lifecycle API** (`src/app/api/tasks/[id]/...`), each requiring an authenticated session:
- `POST /suggest` — if the task has no fixed assignee, considers every user as a candidate; calls `findEarliestSlot`; on success sets `assigneeId`/`scheduledStart`/`scheduledEnd` and flips status to `SUGGESTED`. 409 if nothing fits before the deadline.
- `POST /validate` — requires an assignee + scheduled start/end already set (i.e. must follow a suggestion); flips status to `SCHEDULED`.
- `POST /reject` — clears assignee/schedule and resets status back to `PENDING`, so it can be re-suggested.

**Pages** (`src/app/dashboard/...`): `tasks` (create/manage tasks and drive the suggest→validate/reject flow), `availability` (edit one's own recurring weekly windows), `calendar` (team-wide scheduled view). `src/app/dashboard/layout.tsx` is the shared authenticated shell (nav + sign-out); `src/proxy.ts` is what actually enforces that only authenticated users reach it.

Path alias `@/*` maps to `src/*` (see `tsconfig.json`).
